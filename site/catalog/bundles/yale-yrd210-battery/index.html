Feature · battery

Battery normalization

The manual describes a local low-battery warning. Two upstream implementations adapt a battery value at different layers. Raw reports and final platform values are still needed to explain whether those paths agree for a particular firmware and signature.

No physical-device observations recorded for this feature.

Implementation reasoning

Keep the manual's local battery warning separate from a numeric platform percentage.

The inspected manual explains the warning indicator and replacement batteries, but supplies no value scale for the Zigbee battery attribute. It provides context rather than a numeric binding.

Applies under these conditions

  • Family applicability only; no exact firmware, full signature or raw-scale claim follows from the manual.
  • The upstream PDF is referenced by URL and an inspected digest; it is not included in this package.

Document ZHA's doubling at the cluster attribute stage.

The pinned quirk selects DoublingPowerConfigurationCluster, whose battery_percentage_remaining update multiplies attribute 0x0021 by two. This describes an intermediate value; the final Home Assistant entity pipeline has not been traced in this record.

Applies under these conditions

  • The exact manufacturer/model and full endpoint/cluster signature must select this quirk.
  • Do not infer that the displayed entity percentage is doubled or copy this adjustment into another layer without tracing that layer.

Document Zigbee2MQTT's skipped default halving at the converter stage.

The pinned model entry sets dontDividePercentage to true. The selected converter branch retains the reported percentage instead of applying its default divide-by-two step. This does not contradict a cluster-level adjustment followed by different downstream processing.

Applies under these conditions

  • The selected definition uses a model-string matcher; manufacturer equality is not an enforced constraint there.
  • The percentage must exist and be below 255, and voltageToPercentage must be absent for the cited branch.
  • Source inspection did not execute the converter, test a physical lock or establish cross-platform equivalence.

Open questions

  • No manufacturer definition of the raw battery attribute scale for the exact Zigbee module/firmware has been found.
  • The complete ZHA to Home Assistant entity normalization path is not yet documented.

Help test this feature

For an identified device and firmware, how does an observed raw battery attribute become the platform's displayed percentage?

Proposed procedure; no execution result is implied.

  1. On an already configured device you control, record public manufacturer/model identifiers, firmware if available, protocol, full endpoint/cluster signature and installed platform/driver versions.
  2. During ordinary reporting, capture a sanitized battery attribute value and its attribute identifier, the relevant intermediate conversion if visible, and the final displayed value for the same report/time.
  3. Identify which implementation path the installed version selected, distinguish measured values from deductions, and repeat only as needed to describe normal reporting. No driver patch or device re-pairing is requested.
  4. Submit expected and actual values, time, repetition count and limitations. Keep differences between separate devices or platforms explicit rather than treating them as the same controlled execution.

Requested evidence

  • Public model/signature, firmware or explicit unknown, and exact integration/converter revisions.
  • Sanitized raw and displayed values with enough timing context to associate them; no household/network identifiers or credentials.
  • Any unobservable intermediate stage and whether the result supports, contradicts or leaves the proposed explanation unresolved.

Feature · lock-state

Lock-state context

The referenced device also carries a bounded comparison of ZHA's cluster declaration and Zigbee2MQTT's command/state exposure. It is retained as context, with no complete semantic mapping or hardware result.

No physical-device observations recorded for this feature.

Implementation reasoning

Preserve command exposure and reported lock state as different declarations.

The pinned ZHA quirk declares a DoorLock cluster. Zigbee2MQTT separately exposes a command-capable state field and a reported lock_state field with a not_fully_locked value. These declarations alone cannot establish identical runtime behavior.

Applies under these conditions

  • Do not collapse partially locked or unknown states into a successful requested command.
  • The downstream Home Assistant lock entity is not traced here; no SDF binding or lock-operation experiment is proposed by this bundle.

ZHA quirk

code-declaration · supports

The Yale YRD210 PB DB signature selects a replacement DoublingPowerConfigurationCluster. That cluster multiplies battery_percentage_remaining (0x0021) by two.

  • The full endpoint/cluster signature must also match; manufacturer/model alone is insufficient for quirk selection.
  • This is a cluster-attribute adjustment, not a claim that the final HA entity shows twice the battery percentage.
  • Firmware and downstream ZHA entity normalization are not inspected in this record.
  • zha-yale-realliving · YRD210PBDB220TSLL.signature and replacement
  • zha-battery-cluster · DoublingPowerConfigurationCluster._update_attribute

code-declaration · supports
